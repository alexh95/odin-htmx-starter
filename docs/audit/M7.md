# M7 audit: Ask (the bot on llama.cpp, room mode, the stream client)

An independent security audit of milestone M7 ("Ask", PLAN §14.3, §6.2), by an agent that did not write the code, on
2026-11-05. It applies the review rubric (§19.2.2), the severity scale (§19.2.3, calibrated as M6.md calibrated it) and D15's
crash-zone rules to `features/bot` (domain, web, `room.odin`, views, `backend_llama`, `backend_mock`), both `stores/*/bot`,
`platform/stream/client` (M2's audit debt: its parsers now have a server path), the hub's server-side rows, chat's room-mode
side, `deploy/compose.yaml`, `deploy/promote.ps1`'s new `.env` keys, and `tools/fakellama` so far as it could mislead.

**Method.** Read-only. Another session was using the machine, so nothing was built, checked, tested or run, and no network
host was touched. Every finding comes from reading the source at **`267c2ef`**
(`267c2ef7b1607aba5994e8653e866663d9bee358`, HEAD when the read began); line numbers are at that commit. Another session
changed the working tree during the read and committed `79fc146` and `c21c72d` before it ended. Those are not audited here:
every file was read at `267c2ef`, the changed ones from a `git archive` of that commit. Where it matters, a finding says what
those commits touched; none touches M7-01, M7-02 or M7-03's code. Where a finding rests on the toolchain, `core:nbio`,
`core:encoding/json` and `core:thread` were read at the installed Odin (dev-2026-10, `84bc3fc`). Numbers of bytes are
arithmetic from the code, not measurements. What is inferred rather than read says so, and names what would settle it.
llama.cpp itself was not available to read: every statement about the real server is from memory, and is marked.

**Result (at `267c2ef`).** 0 CRITICAL, 1 HIGH, 2 MEDIUM, 6 LOW, 1 NIT. The HIGH blocks M7's exit by §19.2.1's rule: a hostile or
impersonated llama server kills Houston with one 64 KiB `/props` reply, on a thread with no guard (M7-01). A second way in, past
`MAX_DEPTH`, reaches the loops through the stream. Everything else rated above LOW also needs that server: a generation with
no overall deadline holds its slot for good (M7-02), and a deadline's close frees the receive buffer before the cancel reaches the
kernel (M7-03).

**Privacy.** No path was found by which a member reads a private room's question or a bot answer they shouldn't, on any
transport, or by which anyone reads or writes another's conversation, or a guest reaches a member's. Stop is keyed correctly.
"Checked, with no finding" says what that rests on. No member or guest path to an unbounded resource was found either: every
finding above LOW needs control of the model server, which the code treats (rightly) as outside its trust.

### M7-01 · HIGH · JSON recursion that a server controls

**Where.** `core:encoding/json` has no depth limit: `parse_value` calls `parse_array` or `parse_object`, which call `parse_value`
(`parser.odin:129`, `:200`, `:330`). `backend_llama` knows this (`llama.odin:53`, "the JSON parser recurses") and guards one of its
two callers.

`read_props` (`health.odin:141-152`) has no guard at all. `probe` calls it on up to `MAX_REPLY` (64 KiB) of body (`:24`, `:126`).
It runs on the thread `start_probe` makes (`:51`), and `probe_loop` (`:55-66`) neither calls `guard.thread_init` nor runs inside
`guard.call`. So on that thread `sys.thread_init` was never called and no alternate signal stack exists
(`trap_posix.odin:56-64`), and `tl_frame` is nil, so `_jump_from_trap` declines (`guard.odin:190-196`).

`parse_delta` (`llama.odin:204-241`) does scan first, but the scan counts `{[` and `}]` through the whole text, strings
included, and takes the deepest *relative* count (`:205-215`). `]` inside a string pulls the count below zero, so as many real
`[` after it never pass 32.

**Scenario, the probe.** The port `BOT_LLAMA_URL` names answers `GET /health` with 200, and `GET /props` with:

```
HTTP/1.1 200 OK
Content-Length: 65536

[[[[[[…  (65,536 of them)
```

At most `BOT_LLAMA_PROBE` (5 s) later, `read_props` recurses 65,536 levels, two frames each. The thread's stack is the process's
`RLIMIT_STACK` (`core:thread/thread_unix.odin:79-81`), 8 MiB on Docker's default (inferred: `compose.yaml:30` sets only `nofile`),
so 128 bytes a level overflows it, and `parse_value` holds a `Token` and a `Value` before it calls anything. The fault has no
stack to be delivered on, the kernel kills the process with SIGSEGV: every loop, every stream, no drain, no `CRASH_FILE`.
`restart: unless-stopped` brings it back, and the next probe does it again, so Houston crash-loops for as long as that server
answers so. The frame sizes are inferred; a unit test of `read_props` on a thread of 8 MiB settles it.

**Scenario, the stream.** Any member asks a question. The server sends, many times over, one event of 65,412 bytes, under
`MAX_EVENT`:

```
data: {"a":"]]]…(32,700)…]","b":[[[…(32,700)…[
```

The scan's deepest is 1, and `json.parse_string` recurses 32,700 levels on a server loop. At 256 bytes a level or more (likely,
inferred as above) that overflows. Here the loop has its altstack and `on_sse` a guard, so it is a pure recovery, and `read_event`
returning false ends nothing: `on_sse` ignores it (`:354`), the socket stays open, and the next event does it again. 101
recoveries in 60 s make the next one dirty (`guard.odin:48`, `:174`): the server drains and exits 70, in about a second of the
hostile server's traffic. The suite's `parse_delta(strings.repeat("[", 5000, …))` (`suite_test.odin:99`) passes, because it has no
string in front.

**Who can do this.** Not a member, which is why it isn't CRITICAL. Whoever owns that port: a compromised or malicious llama build
(the model server parses model files and is a far larger target than Houston), another process that won the port on apollo, or
anything on the LAN able to intercept plain http; the bearer key authenticates Houston to the server, and nothing authenticates
the server to Houston. §19.2.3 calls "a crash path that takes down every loop" HIGH without asking who holds the trigger, and
Alex asked exactly this question. Nothing in the fake or its suite sends this.

**Fix.** One proc, `shallow(text, limit)`, that tracks string and escape state and counts absolute depth, used before both
`json.parse_string` calls (it also stops a delta that merely contains 33 `[` of model text being called unreadable). Run `probe`
inside `guard.call`, with `guard.thread_init()` first in `probe_loop`, and treat a crash as Offline. In `on_sse`, a false from
`guard.call` sets `g.problem` and closes. Add cases for both inputs, and a fuzz target over `parse_delta` and `read_props`
(rubric 7). Worth reporting upstream: a `max_depth` on `parse_string`.

### M7-02 · MEDIUM · no overall deadline on a generation

**Where.** `tick`'s two deadlines (`llama.odin:425-433`): first token, measured from `t0`, and idle, `now - g.last`. `read_event` sets
`g.last` first, on every event, before it knows whether the event says anything (`:361-362`). A chunk with `choices: []` is
valid and carries no text (`:233`), so it doesn't move `g.bytes` towards `MAX_ANSWER` either. PLAN §14.3 gives no total, and
nothing else ends a generation.

**Scenario.** After one word, the server sends `data: {"choices":[]}` every 10 s, for good. Or one byte of text every 14 s:
`MAX_ANSWER` takes 42 days to arrive. The generation keeps its slot, `busy` never falls, and with the usual one slot everyone else
queues, then is told the bot is busy once 16 wait (`:260`, `:277`). `/health` stays 200, so `healthy` stays true and nobody falls back
to the mock. On `/bot` the asker can press Stop. In a room there is no Stop by design (§14.3), so the asker stays locked out of
`/bot` and `@bot` alike ("One answer at a time"), `gens.active` holds them until a restart, and nobody can free the slot. Rated
MEDIUM as §19.2.3's "a missing timeout". An honest llama-server stops at `max_tokens` (512), so this needs a hostile or badly
broken one.

**Fix.** `BOT_LLAMA_TOTAL` (say 5 min) from `g.t0` in `tick`, ending as `.Error` when something was said. Move `g.last = now` under
`d.content != ""`, so only words count as life. A queued room ask should have the same bound, measured from its `start`.

### M7-03 · MEDIUM · a deadline's close frees the receive buffer before the cancel is submitted

**Where.** The `Conn`, with its 8 KiB `recv_buf` (`client.odin:67`), lives inside the `Gen`. `end` defers `destroy` with
`nbio.timeout_poly(0, …)` (`llama.odin:480`), and its comment says why: "the client is still on its way out of this callback". But on
Linux a timeout of 0 goes straight on `l.completed` (`impl_linux.odin:737-739`), and `__tick` does its work in this order (`:213-243`):
run `completed`; submit the ring; reap completions. `nbio.remove` only queues an `async_cancel` SQE (`:437-452`). nbio's docs say a
recv's buffers "must remain valid until the callback is fired", and a removed op's never fires.

So a close made during step 3 (a timer's callback, or a recv's) is followed by step 1 of the next tick, which frees the `Gen`, and
only then by the submit that tells the kernel. For most closes that does no harm: `read_event`'s close happens in the recv's own
callback, with `recv_op` already nil, and `on_cancel` runs in step 1, so its cancel goes out in that same tick's step 2. The path
that does harm is `tick`'s deadlines (`llama.odin:434`): a timer callback, in step 3, with a recv armed.

**Scenario.** A hostile server sends comments or empty events continuously and no words, until `BOT_LLAMA_FIRST_TOKEN` passes: first
token is measured from `t0`, so the deadline trips with data still arriving. `tick` closes, the next tick frees the `Gen`, and for
the microseconds to `uring.submit` the kernel still holds a pointer into it. Data that lands then is copied, up to 8,192 bytes of the
server's choosing, into freed heap, which `free` may already have handed on. The window is microseconds and comes once per
generation, at 30 an hour per member, and when it is missed nothing happens. No exploit was tried, and whether the kernel runs that
completion in the window depends on its task-work timing: "suspected" for corruption, certain for the ordering. Not LOW, since
what's on the far side of it is memory corruption with bytes a server chooses; not HIGH, for the window. A quiet server can't
reach it, so an honest idle deadline can't either. This is Linux's nbio, which is what ships; `impl_windows.odin` wasn't read.

**Fix.** Defer `destroy` past the submit: `timeout_poly(time.Millisecond, …)` goes through the ring, behind the cancel's SQE
(`impl_linux.odin:745`), so it can't fire first. Or `next_tick` from `next_tick`. Better, since the client's README promises a Conn
may be freed after `on_close`: put the rule in `client.odin`'s `destroy` comment, or give the client a `release` that does this
itself, since the Pi's agent (M11) inherits it. `get` in `health.odin` keeps its `Reply` on a live stack, so it is not exposed.

### M7-04 · LOW · outside the guard: the client, and what follows a trap

- **The client's callbacks.** `dial_poly`, `send_poly` and `recv_poly` (`client.odin:117`, `:163`, `:177`) are raw nbio callbacks. `feed`
  runs `parse_head`, `chunked_feed` and `sse_feed` on a server's bytes there, on a server loop, with no frame: a trap would kill
  the process. D15 rule 1 is that every entry point is guarded, and §19.2.1 has `tools/check` hold it with an `entry-points` check;
  `tools/check` has no such check (`main.odin:43`). `llama.odin`'s own callbacks wrap only `read_event` and `end`. No trap was found
  in those parsers ("Checked" says why), so this is latent, and a guard costs two lines at the top of the recv callback. The same goes
  for the `timeout_poly(0)` destroy (`:480`), `on_slot`'s and `on_cancel`'s prologues, which do little that can trap.
- **A false `guard.call` is ignored.** `on_sse` (`:354`) goes on as M7-01 says. `tick` has cleared `g.timer` (`:419`), so a trap in
  `emit` leaves no timer running and the deadlines stop for good.
- **`end` emits before it settles.** `end` sets `.Ended` (`:453`), then `emit`s (`:459`), which runs the sink, the view and the stream,
  and only then takes the generation out of `st.gens` and gives its slot back (`:460-464`). A trap in that `emit` leaves `busy` one
  high for good, and the member locked out, since `on_event` never reaches `release`. M2-13 fixed this very thing in the mock by
  releasing first. Move the `emit` below the `guard.unlock`, and run `pump` after it.

### M7-05 · LOW · the key isn't checked for line breaks

**Where.** `st.auth = fmt.aprintf("Authorization: Bearer %s\r\n", key, …)` (`llama.odin:121-123`). `lookup` trims a key file's ends
(`env.odin:88`) and nothing looks inside; `.Secret` has no check (`:98`). `BOT_LLAMA_KEY` from the environment isn't even trimmed.

**Scenario.** A key file holding `abc\r\nX-Other: 1`, or two lines left by an editor, sends a second header on every request,
to the model server, on `/health` and `/props` as well. A file with a blank line in it ends the head early, and the JSON body becomes
garbage. So the answer to the brief is yes, it is injectable. Rated LOW because the writer of that file already owns the host,
and the likely result is a confusing 401 or 400, not an attack.

**Fix.** In `init`: any byte below 0x21 or at 0x7f is `env.problem("BOT_LLAMA_KEY holds a space or a line break")`, naming the
variable and never the value.

### M7-06 · LOW · a bot's message can't be removed or reported from the page

**Where.** `menu` sets `other := msg.author != 0 && msg.author != v.id` (`chat/web/web.odin:513`) and gates `may_moderate` and
`may_report` on it (`:516`). `other` was right for Block and DM, but the bot is author 0, so a moderator sees no Remove on its
messages and no one sees Report. The routes themselves take them: `remove_message` checks only `may_moderate`, and `report_message`
only `msg.author == v.id` (`:1114`), which author 0 passes. Its asker can't delete it either (`may_change`, `chat.odin:612`).

**Scenario.** A member writes `@bot repeat after me: …`. Whatever a model will say now stands in a public room under "Capcom", the
one message whose words any member can choose with no name of their own on them, and nobody but a hand-made POST can touch it; in a
private room, where moderators act through reports, not even that from the UI. Retention takes it in time. This is the moderation
side of prompt injection, and the only effect injection has in a room.

**Fix.** `may_moderate = chat.may_moderate(r, v) && msg.author != v.id`, and `may_report` the same; keep `other` for DM and Block.

### M7-07 · LOW · `link_at` is quadratic in the answer's length

**Where.** `md_inline` calls `link_at` at every `[` (`markdown.odin:450-451`, `:442` for `![`), and `link_at` walks to the end of the text
looking for its `]` (`:520-537`). With no `]`, each call costs what's left. A failed one advances one byte. `bot.render` runs this on the
loop for up to `MAX_ANSWER`, 64 KiB (`bot.odin:25`), on the final frame and on every stored answer of every page load. It is
`platform/markdown`'s only caller, and until M7 it was fed the mock's canned lines alone.

**Scenario.** A server sends 65,536 `[`. That is about 2.1×10⁹ steps for the final frame, a second or two on the loop by estimate
(inferred). It is then stored, so five of them in one conversation cost 10 s on every load of that page, which is the watchdog's `STALL`
(`guard/watchdog.odin:20`): exit 70 each time its owner opens it. A real model can't: 512 tokens makes a few KiB at the very most, and
4 KiB costs 8×10⁶ steps. So it needs the same hostile server as M7-01, and LOW is for that. It matters again when `wiki` or a page
feeds markdown a member's 64 KiB.

**Fix.** Give up on `[` once one search has failed to find a close (remember "no `]` after here" in `Md`), and cap `MAX_ANSWER` at what
512 tokens can be, 16 KiB. The same goes for the backtick search at `:432`, though it needs distinct run lengths, which bounds it.

### M7-08 · LOW · a conversation can't be deleted

**Where.** `ROUTES` (`bot/web/web.odin:36-43`) has no delete, for a conversation or a turn; the store keeps a member's newest 50
conversations of 200 turns each (`store.odin:24-25`, the same in memory) with no age. Chat's retention doesn't apply. A search of
`features/accounts` and its store found no path that removes a member at all, so none that removes these rows.

**Scenario.** A member asks something private, in a house where whoever runs the server can read `dbview` (`/bot` says so). They can't
take it back. It stays in `data.db` and in every nightly backup until 50 newer conversations push it out, which a family's use may
never do. §14.1 treats retention as data minimisation (07 §1.5), and Q20's "for their owner only" invites the expectation that the owner
controls it. The disk bound itself holds: at most about 400 MiB per member at the caps (5,000 × 16 KiB + 5,000 × 64 KiB), which at
30 questions an hour takes a week of nothing else.

**Fix.** A member's Delete on a conversation (`POST /bot/c/<id>/delete`, through the same owner check), and an age limit by job.

### M7-09 · LOW · a failed answer leaves a turn no one replied to

**Where.** `ask` keeps the user's turn at once (`bot/web/web.odin:358`). `on_event` keeps an assistant turn only on `Bot_Done` (`:398`); on
`Bot_Error` it keeps nothing (`:380-383`). A browser that goes away gets an assistant turn of `""`. `bot.request` then sends the last
19 turns as they stand (`bot.odin:98-112`).

**Scenario.** The model is loading, or the slot queue is full, and the question is refused. The member asks again, and the request
holds `user, user`. Many models' Jinja templates refuse that with an error (inferred: from memory of published templates, and it
depends on the model and on llama-server's `--jinja`), which comes back as a refusal, which keeps another user turn. The conversation
then fails until 19 newer turns have pushed the pair out, which can't happen, since nothing succeeds. Only a new conversation gets out.
`fakellama` takes any sequence of roles, so no spec can see this. It hurts only the one member, and only their own history, so LOW.

**Fix.** On `Bot_Error`, keep a placeholder assistant turn, or have `bot.request` merge or skip a run of same-role turns.

### M7-10 · NIT · small things

- **Refusals reach the room.** PLAN §14.3 says a refusal reaches the asker alone. `room_event`'s `Bot_Error` (`room.odin:97-98`) stores
  "The bot is busy…" or "The model is still loading…" in the room as Capcom's message, and a cut-off answer is stored as if whole
  (`:99-101`). `79fc146` changes this path; not audited here.
- **A blank answer.** `cut_body` trims, so all-space text stores an empty message: `store_reply` skips `check_post` (`chat/web/web.odin:456`).
- **The bot's name is free.** At `267c2ef` a member can be called `Capcom`, whose messages look like the bot's (a stored bot message has
  no mark of its own), or `bot`, whom `@bot` both mentions and asks. `79fc146` adds `authz.reserved_name`; not audited here.
- **Room mode skips `Bot_Llama`.** `room_ask` takes `bot.default_backend()` (`room.odin:71`) where `/bot` asks `may_use_llama`. No role
  differs today (`authz.odin:47-50`: `Chat_Post` comes with `Bot_Llama`), but a fork that splits them leaks through here.
- **`a.conn` can go nil between two parts.** In `on_event`, the first `multipart_part` (`web.odin:391`) can close a too-slow stream, whose
  `on_close` nils `a.conn` synchronously; the second (`:395`) then dereferences nil. A pure recovery, inside `guard.call(end)`, so it leaks
  the `Gen`. Check `a.conn` before each.
- **`report` leaks per POST.** `admin_default` calls `report` on every POST, changed or not (`web.odin:506`), and each makes a `fmt.aprintf`
  on the heap that `obs` keeps (`:123`). Admin-only and small. A flapping server does the same at most once a probe.
- **`seen.state` is written without its lock** (`health.odin:48`), after the loops run, while they read it under `seen.mu`. Benign on a
  byte, but the nightly TSan, if it ever runs this path, reports it. Before that write, `seen.state` is zero, which is `.Ready`.
- **A guest can read the llama's state.** `bot.health` is `.Bot_Use` (`web.odin:54`), which guests have, while the comment above the row says a
  guest's badge is the mock's. `/events?t=bot.health` hands them the llama's. Only the word in the badge travels, not the model.
- **`Content-Length` goes through `strconv.parse_int`** (`parse.odin:48`): a sign and a wrap are accepted, the F7/F8 class. Negative means
  close-delimited and a wrap means a short read, both harmless here.
- **For M11, not M7.** The client's WebSocket side has no cap on `c.frag` (`client.odin:277`), and `inbuf` can reach 16 MiB. No server path
  uses it yet.
- **Rubric 7.** The client's parsers, `parse_delta` and `read_props` have no fuzz case; `client_test.odin` has split tests only.

## Checked, with no finding

**A private room's question.** `bot.ask` and `chat.reply` are `deliver` rows. `publish` runs the row and returns before `new_msg`, the
sequence and the ring (`hub.odin:233-236`), so a question is never in a `Msg`; `a_server_side_row_keeps_nothing` holds that. `/events`
refuses a `deliver` row with 400, before any perm (`events.odin:61`), which leaves no replay. The other way in is `hub.subscribe`, and all
four callers pass fixed topics: chat's socket and multipart their own `chat.room`, the ops panel its own, and the lab `lab.room:…`. The
lab's public `publish` route takes only its own two families (`lab/web/web.odin:145-156`), so it can't forge `bot.ask` or `chat.reply`.
No log line carries a payload: only `h.dropped` counts, and `backend_llama` calls no `obs` log at all. `store_reply` and `bot.ask` both go
by the room id in the topic, which chat wrote from `msg.room`. `kind != .Dm` in `announce` keeps DMs out, on the one path that asks.

**A private room's answer.** A bubble goes on `chat.typing:<room>` and the stored reply on `chat.room:<room>`, each with `allow =
room_readable`, which requires `may_read` and the id's one spelling (`chat/web/web.odin:1213-1218`). `out_of_room` kicks all three topics
(`:1069-1073`) on leave, owner's Remove and a moderator's kick; `reaches` finds the member's streams by `s.user` on every transport,
and `subscribe` and `/events` both check the revoke record. So chat.typing can't be replayed after leaving: a new `/events` fails `allow`
with 403 before the ring is touched. A ring frame seen by someone who rejoins within its 10 minutes shows them what the room's history
shows them anyway. `/chat/search` and `/since` go through the same store filters as any message; the bot's row differs only in `author`.
The polling transport sees the answer once stored; it goes through `chat.post`, which bumps the room's version. The model sees the
question alone (`bot.request(0, who.key, nil, question)`, `room.odin:84`), so one room's talk can't reach another's answer. That a
question goes to the model's machine at all is the design, and `/bot` says so; room pages don't.

**Conversations.** `conversation` and `turns` name the owner in SQL (`store.odin:28`, `:63`), and in memory by `find(owner, id)`, answering
`.Not_Found`, and `SQL_TURNS` runs only after that check. `append_turn` re-checks ownership on the writer (`SQL_OWNED`). `conversation_page`
and `ask_member` both pass `v.id`, ids through `parse_id`. `/bot/c*` are `.Account_Self`, so a guest can't reach them. A member on `/bot/ask`
gets `conv = 0`. `/admin/bot` shows `SQL_USAGE_*`, counts and timings, never text. Conversation ids are AUTOINCREMENT, so a dropped id isn't
reused. **Stop:** `stop` compares both `who.member` and `who.key` (`web.odin:465`), so a guest's client key equal to a member's id doesn't
match; `gens.active` is members' only (`admit` returns first for a guest), and the two limits are separate tables. Room generations
have no `gens.owner` row, so Stop finds nothing. Gen ids are sequential and guessable, which the owner check makes harmless. Two guests on
one address share a key and could stop each other's mock.

**Limits a member or guest meets.** `@bot` passes the same `admit` and `members_hour` as `/bot`, keyed by the author, with `leave` first in
`room_done` and on the over-limit path (`room.odin:62-70`, `:114`); a post's own limit and `why_not_post` come first, so a muted member
can't ask, on the form or the socket (`socket_post`). Guests are never on llama and have 5 an hour per client, with stream admission
over them. `gens.owner` holds what's in flight, `gens.active` what members hold, and every path through `ask` reaches `done`, including
admission's refusal (`:352-355`). `MAX_KEYS` clears a limiter at 4,096, but `guests_hour` and `members_hour` are separate. A bubble is at most
4 a second per generation (`BUBBLE_EVERY`), per answer ≤ 16 KiB; a frame past `MAX_MESSAGE`, which 16 KiB of `'` would be at 5×, is
dropped by `publish`, and a topic's ring is capped at 1 MiB. Heap per answer: `Gen` ~8.7 KiB, `pending` drained at 20 Hz, `a.answer` ≤ 64 KiB,
`g.bytes` ending the read at 256 KiB. A slow browser hits `STREAM_MAX_QUEUED`, whose close cancels. A stream's arena holds its `turns` for
its life (M2-21): 8 MiB at the very worst (100 × 16 KiB + 100 × 64 KiB), about 2 MiB with real answers, one per member. `keep` sizes its arena for
what it clones. A question is capped at 4,000 runes and `ASK_CAP`, the prompt at 16 KiB of history. `BOT_QUEUE` is held under `st.mu`.

**The parsers.** *Head:* `head_end` caps it at 16 KiB, checked each read, so ~24 KiB at most; `line[9:12]` has its length check; `colon <= 0` is
skipped; `or_return` handles a bad number. `accept`/`ctype` are cleared before `inbuf` moves; a refused head's only `status` is read after.
The first-token deadline covers a slow head (the probe's `PROBE_WAIT` likewise), and a 3xx is `.Refused`, so no redirect is followed.
*Chunked:* 15 hex digits at most, so `left*16` can't overflow; `min(c.left, len(b) - i)` bounds the copy; a size of 2⁶⁰ allocates nothing
ahead; extensions and trailers are consumed, not kept, and the deadlines end a server that sends them forever; `c.body` and `inbuf` are
cleared per feed, so a read costs at most its 8 KiB. *SSE:* `len(line) + len(data) >= max` holds line and data together, and repeated `data`
lines count their newlines; `event` and `id` are cleared before each write, so each is ≤ `MAX_EVENT`; a comment is capped as a line. `line[0]`
sits behind the `line == ""` case. Events are assembled across chunks and reads before JSON sees them, so a split rune is whole by then.
An event's strings live in `p.data`, on the heap, past any `close`. A `.Sse` body with a Content-Length ends at it; `min()` keeps the slice in range.
Nothing in these three can trap on any input found.

**Invalid UTF-8.** `unquote_string` replaces an invalid byte with U+FFFD, and its buffer counts for it (`parser.odin:412-428`); a lone
surrogate encodes as U+FFFD. Its writes are in bounds for strings the tokenizer admits, and `assert(buf_width <= width)` holds for a valid
rune. So a model's text is valid UTF-8 before it reaches `esc`, SQLite or `cut_body`, and the cuts (`cut_body`, `title_of`) go by rune.
Going out, `json_esc` re-encodes a member's invalid byte as U+FFFD, so a percent-encoded `%FF` can't reach the server's parser either.
`parse_string` sets `context.allocator`, so `destroy_value`'s frees on a bad parse use the temp arena, not the heap.

**Memory ownership.** `end` is idempotent by `phase`; `finish` by `state`; `on_close` follows every `open`, exactly once. `destroy` runs after
`end` returns, a tick later, so `feed` and `read` touching `c` after `on_close` are safe, and a `start` that refuses destroys only a Gen never
opened (nil arrays delete cleanly). `cancel` derefs `g` under `st.mu`, and `end` deletes it from the map before it can be freed. A cancel posted
after the end finds no id. The timer: `tick` clears `g.timer` first; `end` removes it; if a recv and the timer complete in one CQE batch,
`maybe_callback` sees the removal and calls neither twice, and `pool.put` follows (`impl_linux.odin:547-558`). Everything passing through a sink
is on the heap or valid until `on_event` returns, and the request's strings are copied by `body_of` in `start`. `done` nils `c.user` so a later
close finds nothing. Nothing runs `free_all` inside a handler: `on_close` can't run synchronously from `sc.open`, since on Linux `exec` only
queues (`dial_exec`, `:692-719`), and a dial's errors go through `completed`. `on_close`'s nested `free_all` inside `read_event` and `tick` comes after
their last use of temp memory. An nbio callback has the tick's context, whose temp allocator these free, as `workers.on_done` says.

**Threads.** `st.gens`, `st.queue`, `busy`, `limit` and `ep` are under `st.mu` throughout, and `st.mu` and `seen.mu` never nest. `g`'s other
fields are touched only on its loop. Slot accounting across the races: a free slot is taken in `start` or `pump` under the lock; `on_cancel`
beating `on_slot` ends a Queued gen with `ran == false`, and the late `on_slot` gives the popped slot back (`:525-530`); `pump` undoes its
count when a post fails. Posts all happen outside the lock, and through `workers.post`, so a leaving loop refuses them. At most 16 `on_place`
posts per change, under the 128-slot queue. **The probe at shutdown:** `is_closing` ends it within a probe; `publish` drops on `is_closing`;
`pump` goes through the gates; it isn't joined, but `app.exit` doesn't need it. **A generation at drain:** a stream's `on_shutdown` closes it, its
`on_close` cancels by a post to its own loop, and `keep` reaches the writer, which outlives the loops. A room's generation has no stream, so
at `267c2ef` nothing cancels it: the loop waits `SHUTDOWN_FINAL_WAIT`, 500 ms, then releases with the recv pending, the answer is lost, and
`publish` has been dropped anyway. No crash, nothing freed under anyone. (`79fc146` adds a drain.)

**The key.** It is in `st.auth` and in the requests' bytes, and nowhere else: never in a URL (`request` takes it as a header), and nothing in
`backend_llama` logs. `.Secret` shows as "set" on `/admin/modules` (`modules/web/web.odin:80`) and as "…" on `--limits` and in a `record` problem,
and `BOT_LLAMA_KEY_FILE` is no row, so it isn't listed. `parse_url` refuses `@`, so no credential lives in `BOT_LLAMA_URL`. In compose the key
is a file path, mounted read-only, `/dev/null` when unset, with `BOT_LLAMA_KEY_FILE` empty then, which `lookup` treats as unset. On the wire it
is plain http on the LAN, by §14.3's design. Its one weakness is M7-05.

**Prompt injection.** There are no tools and no function calling, so a model's text can only be text. Every place it lands: `piece` escapes
each token alone, so a tag split across tokens is two escaped pieces; `bubble` escapes, under `hx-ignore data-disable-scripting`; `final` and a
stored `turn` go through `bot.render`, under the same two attributes. `platform/markdown` escapes by construction: `resolve_link` admits http(s),
mailto and site paths only, external links get `rel="nofollow noopener"`, and with no `image_prefix` an image is its alt text, so no
fetch-on-view exfiltration exists, and `img-src 'self' data:` would stop one anyway. A clicked link remains possible, which any chat has. A
stored message goes through chat's own `esc`. `failed` shows only this binding's static strings; a server's `error.message` is parsed and
dropped (`read_event` sets a constant). `model_path` is `esc`d on `/admin/bot`. SSE and multipart encode by line and by length, so text can't
forge a frame or a part. **`@bot` loops:** `announce` asks only when `msg.author != 0`, and a bot's message has author 0; an edit never asks. A
bot's text names nobody into an Inbox (same gate), and `seen` skips it. A question's special tokens are the asker's to spend on their own answer;
chat templates parse them (inferred), and there is nothing for them to reach. `SYSTEM` is constant, the question and history go through `json_esc`.

**`/admin/bot`.** Both rows are `.Admin_Modules` and `.Lan_Only`, so a non-admin gets 403 and an off-LAN client 404, by `front` before the body.
`/admin/*` are mounted only on `full`'s main host; `streams` doesn't mount `ADMIN_ROUTES`. The POST passes `same_origin` like any write. `backend` is
matched against the table, and `.Llama` refused unless configured. A change is audited with actor and client, and a no-change isn't.
`audit_store.append`'s result is ignored, as is usual for the log. The switch lasts until restart, and `/admin/modules`' link is a literal, escaped.

**The store.** All values bind; `SQL_COUNT`'s `CASE ?2` handles an empty title; `SQL_DROP_TURNS` runs before `SQL_DROP_CONVS`; enums go through
`enum_from_int`. `0001_bot.sql` is new to SQLite. `start` and `append_turn` trim in the same op.

**Deploy.** `STACK_VALUES`' rules are anchored `\A…\z` and case-sensitive, and read before `.env` is used, so a `$(…)` in `FULL_BOT_LLAMA_URL` is
refused (`promote-test.ps1` holds it). `FULL_BOT_LLAMA_KEY` joins `STACK_PATHS`' rule. A promote edits `.env` by key with `sed`, so the new keys
survive it; only a first deploy writes it whole. Nothing in compose publishes a port or adds a privilege for the bot.

**`tools/fakellama` against the real thing.** Its wire shapes and fault list test the framing well: chunk boundaries inside a line and a rune,
`[DONE]`, stalls, a drop. Three places it could mislead, each from memory of llama.cpp, unverified: (1) it sends a mid-stream error as
`data: {"error":…}`, and a real server may send an `error:` SSE field, which this parser ignores as an unknown field; the stream then ends with no
`[DONE]` and the member reads "cut off", so the outcome is safe, only the words differ. (2) It takes any role sequence (M7-09). (3) It sends nothing
hostile: a head at its cap, a chunk size past 15 digits, deep JSON, a `/props` that isn't JSON. M7-01's two inputs and M7-02's keep-alive pass unseen.
Nothing in it shows a green that a real server would turn red in a way that hurts Houston.
