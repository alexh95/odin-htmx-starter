# M5 audit: ops and status in Houston, runs as data, jobs, backups as a job, and dbview

An independent audit of milestone M5 ("Operate", PLAN §15.4, §22.3), by an agent that did not write the code, on
2026-10-30. It applies the review rubric (§19.2.2), the severity scale (§19.2.3, calibrated as M4.md calibrated it) and
D15's crash-zone rules to everything M5 adds or changes: runs as data in `platform/workers` (the ring, `run_now`,
`cancel_run`, `progress`/`log`/`fail`/`cancelled`, `Job.due`, the scheduler), `features/jobs` with both `store:jobs`
members (the 1 s sync through `write_now`, leases and `fail_lapsed`, `jobs.runs`, `/admin/jobs`), `store.backup`
(`platform/store/sqlite/backup.odin`) and its drill, `features/dbview` with `stores/sqlite/dbview`,
`platform/store/sqlite/adhoc.odin` and the `platform/sqlite` additions, `features/status`' probers, waiters and parts,
the disk and backups parts, `features/ops` in `full` with `obs/store.odin`, `web.prompt_reason`, `cmd/full`'s mounts
and `deploy/compose.yaml`.

**Method.** Read-only. A parity performance run shared the machine, so nothing was built, checked, tested or run: no
`odin build/check/test`, no `build.sh`, no server, no drills, no k6, no Playwright. Every finding comes from reading
the source at `cf7f42b` (`cf7f42b2dc6bb859e7728a8dca5e393cadb9ed00`, HEAD when the read began and ended); line
numbers are at that commit. Where a finding rests on SQLite's own behaviour (what `sqlite3_stmt_readonly` says of
transaction control, when a PRAGMA takes effect, what `sqlite3_db_status` does to the connection), it is from SQLite's
documented contract and its 3.4x source as the auditor knows it, not from a read of the vendored amalgamation; those
points say so and name the unit case that would confirm them. The one untracked file, a perf CSV, was not read.

**Result.** 0 CRITICAL, 0 HIGH, 4 MEDIUM, 6 LOW, 2 NIT. Nothing blocks M5's exit by §19.2.1's rule (0 open CRITICAL or
HIGH); the four MEDIUM findings go to TODO with an owner milestone if they are not fixed in M5. Two of them break an
invariant §15.4 names outright: dbview can leave its reader inside a transaction that pins the WAL (M5-01), and the
live progress and cancel of a long job can't be seen, because the one scheduler thread that runs the job is also the
one that would publish its progress (M5-03).

### M5-01 · MEDIUM · dbview leaves its reader in a transaction, and the WAL pinned

**Where.** `adhoc` (`platform/store/sqlite/adhoc.odin:36-45`) takes the pool thread's reader, prepares the first
statement, refuses a second one and refuses a statement `sqlite3_stmt_readonly` calls a write, then steps it.
SQLite's documented contract is that transaction control (`BEGIN`, `BEGIN DEFERRED`, `COMMIT`, `ROLLBACK`,
`SAVEPOINT`, `RELEASE`) is read-only to `sqlite3_stmt_readonly`, since it changes no database file; only `BEGIN
IMMEDIATE` and `BEGIN EXCLUSIVE` are not. So `BEGIN` passes every check, steps to `DONE`, and leaves the connection out
of autocommit. Nothing ends that transaction: the pool runner (`workers/workers.odin:177-180`) calls `t.run` and
nothing else, `reader()` (`store/sqlite/sqlite.odin:242-249`) runs only the pulled reset, and `pull_reset` (`:278-281`)
acts only after a crash. The pool reader is ended only by `close` at shutdown.

**Scenario.** An admin types `BEGIN` (or `SAVEPOINT a`, or runs `BEGIN` thinking it harmless) and gets an empty answer.
The next query that lands on the same pool thread (one of two) starts a read transaction inside the open one, and its
snapshot now outlives the statement and the 2 s budget: the writer's checkpoints can't pass it, so the WAL grows with
every write until the process restarts (S0.6 measured 165 MB in 5 s under load), and every later dbview read on that
thread sees the database as it was. This is exactly what §15.4 gives dbview its budget for ("a long read snapshot pins
the WAL"); the budget bounds a statement, not a transaction. The admin gets no sign of it. `COMMIT` would end it, if
they knew which thread held it.

The same gap lets PRAGMAs change the shared reader: SQLite applies a setting PRAGMA (`cache_size`, `mmap_size`,
`busy_timeout`, `case_sensitive_like`, the flag PRAGMAs such as `reverse_unordered_selects`) while it *prepares* the
statement, so `adhoc`'s read-only refusal comes after the change has been made, and some settings
(`temp_store_directory`) are process-wide. Today only dbview uses the query pool, which limits the reach to dbview
itself and that one global; the pool is meant for bm25, exports and the backup too (§11.8, D16).

Certain for `BEGIN` from SQLite's contract and the code; a unit case confirms it in a few lines: `adhoc("BEGIN")`, then
`adhoc("SELECT 1")`, then `sqlite.in_transaction(reader.db)` is true. The PRAGMA timing is from SQLite's source and is
"suspected" here until the same kind of case (`PRAGMA reverse_unordered_selects=1`, then a read of it) is run.

**Fix.** Install a `sqlite3_set_authorizer` on the pool reader around `adhoc`'s prepare (it needs a binding in
`platform/sqlite`) that allows only `SQLITE_SELECT`, `SQLITE_READ`, `SQLITE_FUNCTION` and `SQLITE_RECURSIVE` and denies
the rest (`SQLITE_TRANSACTION`, `SQLITE_SAVEPOINT`, `SQLITE_PRAGMA`, `SQLITE_ATTACH`, `SQLITE_DETACH`, …): the
authorizer runs during prepare, before a PRAGMA's effect, so it closes both halves, and `stmt_readonly` and
`LIMIT_ATTACHED` stay as the second line. Also end anything left: after the step, `if sqlite.in_transaction(conn)
{ ROLLBACK }`, and the same check before each pool task. `dbview.spec` cases: `BEGIN`, `SAVEPOINT a` and
`PRAGMA cache_size=1` refused; and a drill line that the WAL checkpoints after a dbview session.

### M5-02 · MEDIUM · the writer's connection is used by two threads at once

**Where.** M5 makes the writer thread report its connection's memory after every batch and every idle wake:
`report_memory(&db.writer, 0)` at `writer.odin:151` (after `ping()` has released `db.wlock`) and `:160` (after
`commit_batch`'s deferred unlock), which calls `sqlite.db_status` three times on `db.writer.db`
(`store/sqlite/sqlite.odin:316-322`) with no lock. Meanwhile the scheduler thread runs `write_now` (`writer.odin:77-86`)
on the same `db.writer.db` under `db.wlock`: `jobs.sync`'s save every second (new in M5), `fail_lapsed` and `prune`,
and M4's `contacts.reset`. The connections are opened `OPEN_NOMUTEX` on a `SQLITE_THREADSAFE=2` build
(`app/prepare.sh:86`, `platform/sqlite/sqlite.odin:54`): "one connection per thread, or under the writer's lock", as the
flag's own comment says. `report_memory` breaks that rule.

**Scenario.** Every second the two can overlap: the writer finishes a batch and unlocks, the scheduler takes the lock
and starts its upserts, and the writer, unlocked, measures the connection. `SQLITE_DBSTATUS_STMT_USED` is not a plain
read: SQLite measures it by pointing `db->pnBytesFreed` at a counter, narrowing the lookaside bounds, and "deleting"
every statement on `db->pVdbe` in a counting mode, then restoring both. A free on the scheduler's thread during that
window is counted instead of done (a leak), the walk of the statement list races a prepare that links into it, and on
a weakly ordered CPU a lookaside slot can reach `sqlite3_free`. Most overlaps will cost a few leaked bytes; the rest are
memory corruption inside SQLite, which by D15 is dirty: exit 70 with no recorded reason that points here. The race is
certain from the code; its worst consequence is "suspected", from SQLite's source. TSan would report it if any test ran
`write_now` beside the writer task (the nightly TSan run covers the writer and workers' tests separately).

**Fix.** Measure under the lock: call `report_memory` inside `commit_batch` before its unlock and inside `ping` while
it holds `db.wlock` (or have `write_now` report too, under its lock, and drop the unlocked calls). One more
reader-side check: `on_reader_tick`'s `report_memory(r, …)` (`sqlite.odin:306`) runs on the reader's own loop, which is
fine; keep it so.

### M5-03 · MEDIUM · one scheduler thread: a long job hides its own progress and stops every other job

**Where.** The scheduler (`workers/jobs.odin:255-321`) runs each due job inline, "one job at a time", and `full` mounts
on it `ops.sample` (1 s), `jobs.sync` (1 s), `store.backup` (10 min, nightly), `lab.bus` and `contacts.reset`
(`cmd/full/routes.odin:85-91`). `jobs.sync` is the only path from a run's in-memory state (`progress`, `log`, Running)
to the store and to `jobs.runs`. For a run `due` started, the scheduler creates the run and marks it Running in the
same locked section (`:278-292`), so no sync ever sees it queued.

**Scenario.** While `store.backup` copies, nothing else on the thread runs: `jobs.sync` doesn't, so the page never
shows the backup Running or its "1 of 3", and the row a viewer sees is the one sync last wrote; for the nightly run there
is no row at all until it ends, so its Cancel button (`views.odin:65-67`, shown only for a queued or running row) never
appears; `ops.sample` doesn't, so the ops panel and its sparklines stop; `lab.bus`'s beat stops on the lab host; the
demo reset's minute check waits. Today's Houston database is small and a backup takes well under a second, which is
why no spec could catch a running backup (TODO slices 5 and 6 say as much and leave live progress and a running cancel
to workers' unit test). But the feature's contract (§15.4: progress rows upserting over `jobs.runs`, cancel with a
reason) is unobservable by construction for exactly the jobs it is for, and the jobs PLAN lists next (the weekly FTS
`optimize`, the video import scan, retention sweeps) are longer. §11.8 also says the nightly backup runs "from the query
pool as a job"; it runs on the scheduler.

**Fix.** Separate dispatch from running: the scheduler decides what is due and hands each run to a jobs pool (§6.2
names one), setting `tl_run` on the thread that runs it, so `jobs.sync` and `ops.sample` keep their second; or, at
least, give the two 1 s jobs their own timer and run `store.backup` on a thread of its own. Keep "one run per job at a
time" with `Job_State.running`. Then the spec the TODO deferred becomes possible: a backup made slow (a large seeded
file, or a test hook) shows Running and its progress live and can be cancelled from the page.

### M5-04 · MEDIUM · a backup cut short stays as a backup

**Where.** `backup_job` (`backup.odin:84-92`) runs `VACUUM INTO` straight to `backup-<date>-<time>.db`, which SQLite
creates at the start and fills as it goes. `newest_backup` and `backup_names` (`:165-195`) count any `backup-*.db` by
its name and modification time; `backup_due` (`:63-69`) skips the night when the newest is under 20 h old; status's
`backups` part shows its age; `prune_backups` (`:157-163`) keeps the newest seven by name. At shutdown,
`workers.unschedule` only sets a flag (`app/app.odin:283`, `jobs.odin:247-250`: "exit doesn't wait for it"), and the
drain is bounded at a few seconds.

**Scenario.** A deploy (`promote.ps1`), a crash or the OOM killer lands while the nightly backup is copying. The process
exits mid-copy and leaves a truncated `backup-…db`. On the next boot status says "the newest is 2 min old", `ok`;
`backup_due` at the same hour finds a backup under 20 h old and skips the night; the next nights rotate it into the
seven kept, so a week later it is one of the restore points an operator picks from, and the first one they try. Nothing
checks a backup after the run that wrote it. The drill can't see this: it waits for the file name to appear, sleeps
300 ms "the copy is checked after it is written", and stops the server (`tools/drills/drills.mjs`, `phaseBackup`); on a
large database that is the same race.

Separately, on any VACUUM failure the job removes `dest` (`:89-91`). `VACUUM INTO` refuses an existing non-empty file
(§11.8: "refusing to overwrite"), and two runs can name the same second when the clock steps back (NTP), so the cleanup
can delete the earlier backup it collided with.

**Fix.** Copy to `<name>.part`, quick-check it, then rename to the final name (atomic on one filesystem); at
`backup_init`, remove any `backup-*.db.part`; never count `.part` files. Remove `dest` only when this run created it
(check `os.exists` before the copy and fail early if it does). In the drill, poll the job's state (the run's row, or
the log endpoint) instead of the file's name.

### M5-05 · LOW · Run now rotates out the nightly backups

**Where.** `prune_backups` (`backup.odin:155-163`) keeps the newest `BACKUP_KEEP` (7) `backup-*.db` files, whoever
asked for them.

**Scenario.** An admin runs `store.backup` by hand a few times while testing (the backup drill does the same on a
server of its own), or a confused admin clicks seven times in an incident. Each run removes the oldest nightly copy; after
seven, the directory holds seven copies of the last few minutes and no restore point from before them. That is the
week of history §11.8 keeps, lost at the moment it is most likely to be wanted (an incident, a bad write). Each click
needs Admin_Jobs, the LAN, a step-up and a reason, and is audited, so this is a foot-gun, not an attack.

**Fix.** Name by-hand copies `manual-<date>-<time>.db` with a keep of their own (or none: an admin deletes them), and
keep `backup-*` for the nightly ones; or keep the newest nightly per day for `BACKUP_KEEP` days.

### M5-06 · LOW · `close` frees the writer's connection under a running `write_now`

**Where.** `shutdown` stops the scheduler only by flag (`app/app.odin:283`); `main` then calls `store_sqlite.close`
(`cmd/full/main.odin:74`), which joins the writer task and then finalizes, closes and zeroes `db.writer` (`open.odin:
139-158`) without taking `db.wlock`. The scheduler may be inside `write_now` (`writer.odin:77-86`) at that moment:
`jobs.sync` runs every second and holds the lock for its upserts; the demo reset's job can too.

**Scenario.** Rare: the shutdown's last steps overlap a sync. Then `sqlite3_close_v2` runs on a connection another
thread is stepping, and `db.writer = {}` clears the statement cache under `writer_stmt`. The likely result is an exit
70 instead of 0 at a deploy, with a crash line that names shutdown; the database itself is protected by SQLite's WAL
(the open transaction is rolled back on the next open). M5 raises the odds from once a minute (M4's demo reset) to
once a second.

**Fix.** Make `unschedule` wait, bounded by the shutdown's grace, for the scheduler to leave its current job (join the
thread; a long job checks `cancelled()`, which `unschedule` can set on the running run); and in `close`, take
`db.wlock` before closing the writer, with `write_now` refusing (`false`) once `db.is_open` is false, checked under the
lock.

### M5-07 · LOW · dbview shows secrets, and its audit can be padded

**Where.** dbview reads any column: `users.totp_secret` (in the clear since M4), the argon2id password hashes, the
session, reset and invite hashes. The audit entry is written before the query runs with only `sql[:200]`
(`dbview/web/web.odin:221-224`), out of up to 4,000 bytes (`dbview.odin:107`).

**Scenario.** An admin runs `SELECT '<190 spaces>', username, totp_secret FROM users`. The audit row shows a string of
spaces; the result holds every member's TOTP seed. With a member's password (phished, reused) that admin, or whoever
holds an admin's stepped-up session, now passes that member's code step too. PLAN gives dbview to Admin_Db and says
nothing about masking, so reading secrets is within the plan's trust model for an Admin; the plan does mask secrets
elsewhere (D10: `/admin/modules` shows "set" for a secret env row), and §17.7 relies on the audit to say what an admin
did, which the 200-byte cut defeats.

**Fix.** With M5-01's authorizer, answer `SQLITE_IGNORE` for `SQLITE_READ` of the secret columns (the column reads as
NULL), listed by each store next to its migration (accounts: `users.totp_secret`, `users.password`, the hash columns).
Audit the whole SQL (it is capped at 4,000 bytes already) or its first 200 runes plus a SHA-256 of the rest.

### M5-08 · LOW · one value can be a gigabyte

**Where.** `adhoc` caps rows (200) and the characters shown of a cell (200) after SQLite has produced the value
(`adhoc.odin:58-68`, `:79-92`), and stops a statement past 2 s through a progress handler that SQLite calls between
VM steps. `SQLITE_LIMIT_LENGTH` stays at SQLite's default, 1,000,000,000 bytes.

**Scenario.** `SELECT length(randomblob(999999999))`, or `printf('%999999999c', 'x')`, allocates and fills about 1 GB
inside one function call, where no progress callback runs. The pool has two threads, so two such queries (the queue
takes 64) hold 2 GB at once; a container with a memory limit is killed. It needs Admin_Db, the LAN and a step-up.

**Fix.** At `open_reader` for a pool thread (or around `adhoc`), `sqlite.limit(conn, LIMIT_LENGTH, 1 << 20)` and a
`LIMIT_SQL_LENGTH` of `MAX_SQL`; add `LIMIT_LENGTH :: 0` beside `LIMIT_ATTACHED`. A spec case: `randomblob(2000000)`
answers SQLite's "string or blob too big".

### M5-09 · LOW · the probes' timeouts don't cover connect and resolve

**Where.** TODO slice 3 asks for "`STATUS_PROBES` externals with 2 s timeouts (connect and resolve included)" and is
checked off. `probe` (`status/status.odin:174-191`) still calls `net.resolve_ip4` and `net.dial_tcp` with no timeout,
then sets 2 s receive and send timeouts that apply to each `recv`, in a loop that reads until 2 KiB or close.

**Scenario.** An external whose address drops packets (a powered-off Pi on the LAN) holds its prober in `connect` for
the kernel's SYN retries, about two minutes on Linux, on each attempt. Pages stay bounded (the 2.5 s cut-off answers
"no answer in 2 s"), so this is not a page stall; but the card keeps the last real answer's age growing, and a peer
that sends a byte every 1.9 s keeps the prober in the read loop indefinitely. PLAN's "As built (M3)" says connect and
resolve have no timeout of their own; the M5 TODO line claims otherwise.

**Fix.** A non-blocking connect with a 2 s poll (or `SO_SNDTIMEO` on Linux, which bounds `connect`), an overall
deadline on the read loop (`PROBE_TIMEOUT` total, not per `recv`), or reword the TODO line to what was built.

### M5-10 · LOW · raw mutexes around shared state

**Where.** `stores/memory/jobs/store.odin:19-23` adds a `sync.Mutex` of its own; no other memory store has one (they
share their family's lock). `sched.mu` (`workers/jobs.odin:84-94`) predates M5, but M5 makes loop handlers take it
(`run_now`, `cancel_run`, `job_state` from `/admin/jobs`), and holds it across `append`s into a caller's array
(`runs_since`, `:174-186`). Rubric item 4 asks for locks only through `guard`, and §19.2.1 lists a `tools/check locks`
rule ("no `sync` lock outside the guard helpers") that `tools/check` doesn't implement.

**Scenario.** A trap while one of these is held (an allocation failure in `runs_since`'s `append`, or in the memory
store's clones) is a pure crash by D15's counters, since guard doesn't know the lock: the guard recovers, the lock stays
held, and the next `/admin/jobs` request blocks its loop until the watchdog exits 70, naming the wrong request. Unlikely,
and the memory jobs store is in no hosted profile.

**Fix.** Use `guard.Mutex` with `guard.lock`/`guard.unlock` for `sched.mu` and the memory store (or the memory family's
shared lock); copy the ring under the lock into a fixed local array and append outside it. Either add the `locks` check
or strike it from §19.2.1.

### M5-11 · NIT · the jobs store's globals are written outside the lock that reads them

**Where.** `save`, `fail_lapsed` and `prune` (`stores/sqlite/jobs/store.odin:31-37`, `:80-98`, `:100-117`) pass their
arguments to `write_now`'s callback through package globals, set before `write_now` takes `db.wlock`. Today every call
is on one thread at a time (`fail_lapsed` at boot, before `schedule` starts the scheduler; then only the scheduler), so
there is no race; a second caller (a test that runs a sync beside the scheduler, an admin "prune now") would make one
save write another's rows.

**Fix.** Give `write_now` a `rawptr` (`write_now(proc(data: rawptr) -> bool, &args)`), or say "scheduler thread only"
in the contract and assert it.

closes for sequential tries from one client (the e2e case), and case folding is safe: usernames are ASCII by
`check_username`, so `strings.to_lower` and `COLLATE NOCASE` agree on every name that can exist. Disabled accounts
fall through to the ghost path as unknown names do. Two ways to tell names apart remain: concurrent tries
(M5-17) and targeted slot eviction (M5-18).

**M4-09: partly.** The `/events` part is right:
- `revoke_session` records the revoke under `h.mu`, before posting any kicks.
- `/events` reads the record under the same `h.mu` hold as `join_loop`. So a stream either has its inbox counted
  before the kick is posted, and `add_sub` runs on the same loop before that loop's drain, or it finds the record.
- `ctx.start` and the record's `at` are both `sys.mono_ns()` (`front.odin:35`), so the clocks agree.
- `viewer.session` is never 0 for accounts (`| 1`), and identities without sessions keep 0, which only a full
  revoke matches.
- Session keys are 63 bits of the session's SHA-256 hex and also matched on user id, so a collision is not a
  practical concern.
- The revoked branch releases its replay refs and leaves `watch` unset. Unsubscribe calls no watcher it never
  told, so open and close stay balanced.
- The only false positive is benign: a full `revoke` (role change, disable, reset) also kicks a stream whose
  request started before the record but loaded the new grant. That page goes to sign in once.

What's missing: per-session kicks match only `/events` subscribers. A stream subscribed through `hub.subscribe`
has `session` 0 and isn't on the member topic. Neither kind of revoke reaches it, and in `full` that stream is the
ops panel (M5-16).

**core.js kicked-page wait: closes the Firefox abort.** htmx 4's HX-Redirect sets `location.href`, which fires
`beforeunload` within the 500 ms, so the sign-out's own navigation wins. A page that is only revoked (another
device revoked it) goes to sign in after 500 ms. The flag is sticky, though (M5-21).
